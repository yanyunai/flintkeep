# 补充分析：探测归属、Agent 写入契约、数据库/容器级联启停

> 本文是 `docs/12-我的项目-独立页与菜单栏落地规划.md` 的补充设计，确认后并入该规划。

---

## 1. 探测是我们程序自己的功能，跟 Agent 没关系

对，探测完全在应用后端内部跑，Agent 不参与、也感知不到：

| 谁 | 做什么 | 何时 | 是否耗 token |
|---|---|---|---|
| **Agent（MCP）** | 一次性写「静态项目档案」：名称、路径、启动方式、端口、访问地址、备注 | 项目接入 / 命令变更时 **1 次** | 只有这 1 次 |
| **应用后端 `project-probe.ts`** | 每 3s 对登记的端口做 TCP 握手，算状态，SSE 推给页面和菜单栏 | 持续运行 | **0** |
| **你（页面 / 菜单栏）** | 点「启动」「关闭」 | 按需 | 0 |

- 探测是纯 Node `net.connect`，不调模型、不调 MCP、不走网络请求到外部。
- Agent 写完档案后**读盘即生效**，不需要上报、不需要重启应用、不需要再调一次工具确认。
- 状态是实时计算的、不落库，所以应用关掉时探测也不跑；下次打开 3 秒内第一轮扫描就能看到全部项目当前状态（包括别的 Agent 在终端起的）。
- Electron 托盘只是通过 `http://127.0.0.1:8787` 读状态、发启停命令，本身不做探测。

## 2. Agent 写入契约：它到底该写什么

### 2.1 一条原则：只写静态元数据，运行态一律禁写

`status / pid / pgid / startedAt / source / logs` 全部由探测层生成，**Agent 不能写**。
这样才保证：反复启停 0 次 MCP 调用、状态永远可信、Agent 不会因为「以为自己在跑」而写脏数据。

单个工具 `project_upsert(project)`，按 `id` 幂等覆盖（重复写同一 id 是更新，不会重复登记），支持只传要改的字段（改端口不用重传整份启动流程）。写入后**直接返回校验结果 + 写后的完整档案**，Agent 一次调用就能确认，不用再查一次。

### 2.2 字段清单（六组）

| 组 | 字段 | 类型 | 用途 / 校验 |
|---|---|---|---|
| **身份** | `id` | string | 必填，slug（`^[a-z0-9_-]+$`），幂等键 |
| | `name` | string | 必填，显示名 |
| | `notes` | string | 备注，自由文本（给人看） |
| | `tags` | string[] | 分类标签 |
| **位置** | `cwd` | string | 必填，绝对路径，写入时校验目录真实存在 |
| | `pathMac` | string | 可选，跨平台备用路径 |
| **启动方式** | `commands[]` | `{cmd, kind, cwd?, timeoutMs?, env?}[]` | 必填，有序；`setup` 串行等退出码 0，`service` 常驻；至少一条 service；每条必须有超时 |
| | `stopCommand` | string | 可选，覆盖默认的 kill（**容器节点必须给**） |
| | `kind` | `process \| compose \| docker` | 默认 `process`，决定启停与探测方式 |
| **访问 / 探测** | `probe.ports` | number[] | 判活目标，1–65535，可多个（如前端 8790 + 后端 8787） |
| | `probe.url` | string | 「打开」按钮的访问地址；建议限制 `127.0.0.1/localhost` |
| | `probe.healthUrl` | string | 可选，HTTP 健康检查，区分「端口被别的服务占了」 |
| | `probe.mode` | `any \| all` | 多端口判活策略，默认 `any`（任一通就算活） |
| **依赖** | `dependsOn` | string[] | 依赖的项目 id，见第 3 节 |
| | `stopPolicy` | `self \| cascade \| keep` | 默认 `self`，见第 3 节 |
| | `shared` | boolean | 是否为多个项目共用的依赖 |
| **归属** | `registeredBy` | string | Agent 名/ID，仅审计用，不参与状态判定 |
| | `updatedAt` / `version` | — | 服务端自动填，便于审计与回滚 |

### 2.3 几个容易踩的点

- **端口和访问地址要分开**：一个项目常有多个端口，但只有一个主入口。`ports` 用于判活，`url` 只用于「打开」按钮；不要把 `probe.url` 当探测目标去解析。
- **多端口判活**：默认 `any`（前端起来了就算跑着）；前后端都必须在这类项目用 `all`。也可加 `criticalPort` 指定主端口，避免「后端挂了但 Vite 还活着」显示成 running。
- **备注别承载逻辑**：`notes` 里写「共享库，别停」人也看得懂，但程序绝不能去解析自然语言；是否共享必须用结构化字段 `shared: true` + `stopPolicy`。
- **校验放服务端，一次做完**：cwd 存在、端口合法、url 回环、命令不为空、依赖 id 存在、无循环依赖、compose 文件存在。失败直接把原因返回给 Agent，让它一次改对。
- **安全**：`project_upsert` 放进 `FULL_ONLY_TOOLS`（`src/core/mcp.ts:57-60`）受 `agentPermission` 约束，写入走 `log_agent_action`（`mcp.ts:132-133`）审计；命令里禁止明文密钥，用 `${ENV}` 引用；档案文件权限 600。
- MCP 工具定义风格跟现有一致：`src/core/mcp-meta.ts:50-58` 的 `add_asset` / `update_asset` 用 `{type:'object', properties, required}`，照抄即可。

### 2.4 一次写入的样例

```json
{
  "id": "flintkeep",
  "name": "密钥管理",
  "cwd": "/path/to/project",
  "notes": "开发时前端 8790，后端 8787；共用 pg-main，停本项目不要停库",
  "tags": ["桌面应用", "日常开发"],
  "kind": "process",
  "commands": [
    { "cmd": "npm install", "kind": "setup", "timeoutMs": 180000 },
    { "cmd": "npm run dev", "kind": "service" }
  ],
  "probe": { "ports": [8787, 8790], "url": "http://127.0.0.1:8790", "mode": "all" },
  "dependsOn": ["pg-main"],
  "stopPolicy": "cascade",
  "registeredBy": "claude-code"
}
```

写完之后，你点启动/关闭、应用重启、项目反复启停，**都不需要 Agent 再来一次**。

## 3. 数据库 / 容器 / 其他项目，能不能连带停掉？

**能，而且建议不写「容器专用逻辑」：把依赖本身也登记成一个普通项目节点，用 `dependsOn` 连成依赖图。** 这样探测、日志、页面、菜单栏、启停全部复用同一套代码，改动最小。

### 3.1 依赖节点长什么样

```json
{
  "id": "pg-main",
  "name": "共享 Postgres",
  "kind": "compose",
  "cwd": "/path/to/project",
  "commands": [{ "cmd": "docker compose up -d postgres", "kind": "setup", "timeoutMs": 120000 }],
  "stopCommand": "docker compose stop postgres",
  "probe": {
    "ports": [5432],
    "docker": { "composeService": "postgres", "projectName": "infra" }
  },
  "shared": true,
  "stopPolicy": "keep",
  "notes": "被 3 个项目共用，别自动停"
}
```

关键点：**容器节点必须显式给 `stopCommand`**。否则探测层按默认逻辑去 kill「`docker compose up -d`」这个早已退出的 CLI 进程，容器其实还在跑 —— 这是最容易踩的坑。

### 3.2 启停顺序

- **启动**：拓扑序（依赖先起）→ 每个依赖等 `probe` 就绪（`readyTimeoutMs`，默认 60s）→ 再起主项目。依赖没起来就中止，标 `failed` 并在日志里写清「等 pg-main 超时」，不要傻等或硬起。
- **停止**：逆拓扑序（先停主项目，再处理依赖）；依赖是否停由 `stopPolicy` 决定：

| `stopPolicy` | 行为 |
|---|---|
| `self`（默认） | 只停自己，依赖一律不动 —— 最保守 |
| `cascade` | 连带停**独占**依赖（`shared:false` 且引用计数归零） |
| `keep` | 永远不随项目停（数据库、Redis、MQ 建议用这个） |

### 3.3 共享依赖是最大的风险，必须用引用计数

`pg-main` 被 3 个项目引用时，停掉其中 1 个**绝不能停库**，否则另外 2 个当场挂掉。所以：

- 计算「当前 running 的项目里还有几个 `dependsOn` 指向它」，**归零才允许停**；
- `shared: true` 的节点默认 `keep`，即使归零也不自动停；
- 页面上给两个明确动作：**「停止本项目」** 和 **「停止本项目及依赖」**，后者弹窗列出「将一并停止：pg-main、redis-cache…」再确认；
- 菜单栏同款，折叠显示 `● 密钥管理（含 2 个依赖）`，子菜单两个停止项。

这就是你说的「连容器里对应的数据库、还是跑的其他什么项目，也直接停掉」——能做到，但前提是**登记过归属关系**，不能靠「同网段 / 同目录 / 端口相近」去猜，猜就会误伤。

### 3.4 容器探测比 TCP 握手复杂，要三路并用

| 手段 | 解决什么 |
|---|---|
| `probe.ports` TCP 握手 | 快速判活（沿用现有 `portOpen()`） |
| `docker compose ps --format json` / `docker ps --filter label=...` | 容器到底在不在，CLI 进程退出也看得见 |
| `docker inspect --format '{{.State.Health.Status}}'` | 区分 running 但 unhealthy（数据库还在初始化） |

归属只能按 **compose project name + service name / label**，不能按镜像名或端口。
可移植的现成封装在 `workbench/server/services/sandbox.js:21-34`（`dockerAvailable` / `containerRunning` / `containerExists`）、`:61-65`（`docker ps --format {{.Ports}}`）、`:9-19`（带 timeout 的 `run()`），约 60 行。`flintkeep` 目前**没有任何 docker 代码**，需要新增。

Docker Desktop 没开、命令超时、没权限时返回 `unknown` 而不是 `stopped`，避免误判后反复重启。

### 3.5 停容器的安全红线

- 用 **`docker compose stop <service>`**（保留容器与网络，恢复最快）；**不默认用 `down`**（会删容器和网络）；**绝对禁止 `down -v`**（删卷 = 删数据库数据）。
- 停之前列出将受影响的容器名，二次确认。
- 按 **service 粒度**停，不要整份 compose 一起 down —— 一份 compose 里可能还跑着别的项目要用的 Redis。
- 数据库类节点建议默认 `keep`：开发时项目停了库继续跑最省心，真要停就手动点。
- 系统级数据库（`brew services` / 系统 Postgres）不是容器，只能按端口探测，停止必须给显式命令，**不要 kill 系统进程**；远程数据库探测不到本机端口，标 `external` 或跳过即可。

### 3.6 写入时就校验，别等运行时炸

`project_upsert` 落盘前检查：依赖 id 全部存在、无环（A→B→A）、`compose.yaml` 在 `cwd` 下存在、`composeService` 在文件里存在、`stopCommand` 对容器节点必填。校验失败直接把原因回给 Agent，一次改对。

### 3.7 落到界面

- 页面：依赖缩进/树状展示，启动时显示「等待 Postgres 就绪…」，停止时弹窗列出将停清单；
- 状态徽标增加 `unknown`（Docker 不可用）和 `waiting`（等依赖就绪）；
- 菜单栏：折叠显示依赖数 + 两种停止动作。

## 4. 结论

1. **探测是程序内部功能**，跑在后端 3s 一轮的 TCP 握手，与 Agent/MCP 完全解耦，不耗任何 token。
2. **Agent 只写一次静态档案**：身份 / 位置 / 启动方式 / 访问与探测 / 依赖 / 归属六组字段；运行态禁写，写入即生效，之后反复启停 0 次 MCP 调用。
3. **数据库、容器、其他项目能连带启停**，用「依赖也登记成项目节点 + DAG 拓扑启停 + 共享引用计数 + `stopPolicy`」实现，代码复用度最高；但必须先登记归属，且默认保守（共享依赖不停、禁 `down -v`、停前二次确认）。

---

## 5. 策略默认（按本轮确认修正）

1. **关闭项目时，独占依赖（包括容器里的数据库）默认一起停** —— 这是本轮明确要的效果，修正上一版「数据库默认 keep」的保守建议。
2. 只有 `shared: true` 的共享依赖才保留（引用计数归零也不自动停）；要停共享依赖，用页面 / 菜单栏的「停止本项目及依赖」并二次确认。
3. 容器一律按容器粒度停，具体命令由档案里的 `stopCommand` 决定；禁止进容器 kill 数据库进程、禁止 `down -v`。

## 6. 补充澄清：按钮控制容器、容器粒度、Mac 的 O 软件

### 6.1 「应用里没有 Docker 代码」是什么意思

指的是 **flintkeep 这个管理应用自身的源码里**没有调用 docker 的能力（没有 `docker ps` / `docker compose stop` 这类代码），**不是说你电脑上没有 Docker、更不是说项目不能用容器**。

- 启动命令里写 `docker compose up -d`，shell 本来就会执行，不需要应用懂 Docker；
- 但要让应用能**探测容器是否真在跑 / 是否 healthy / 按容器粒度停**，需要在 `project-probe.ts` 里新增约 60 行调用 docker CLI 的逻辑，可直接移植 `workbench/server/services/sandbox.js:9-34,61-65`。

这是「要新增哪几行代码」的盘点结论，不是功能障碍。

### 6.2 按钮能不能控制带容器的项目：能

- **启动**：按 Agent 写好的 `commands[]` 顺序执行 —— 容器数据库 → 后端 → 前端，每步等就绪（端口/健康检查）再走下一步。
- **关闭**：执行档案里的 `stopCommand`，把容器数据库一起停掉，再停后端/前端（逆序）。
- **程序不需要理解容器里装了什么**：停整体还是停某个 service，是 `stopCommand` 决定的配置选择（`docker stop <容器名>` 或 `docker compose stop <service>`），你也能在页面上改；程序只负责执行 + 用端口/docker 状态确认停没停。

### 6.3 关整个容器，还是只关容器里的数据库？→ 按容器粒度停

**结论：关整个容器，不要进容器里 kill 数据库进程。**

| | 说明 |
|---|---|
| Windows 那种「一个容器里放了数据库+项目」 | 停整个容器 = 数据库和项目一次全停，正好是你要的效果，最简单 |
| Mac 现在这种「一容器一服务」 | 停 `yanyun-pg` 容器就等于停那个数据库，两者等价 |
| 为什么不能只 kill 库进程 | 容器里数据库常是 PID 1，kill 它容器照样退出；还可能被 restart policy 自动拉起，反而停不掉；状态也更脏 |
| 用什么命令 | `docker stop <名>` / `docker compose stop <service>` —— 保留容器和数据卷，下次 `start` 秒级恢复；**绝不 `down -v`**（删卷=删数据） |

唯一要防的是**一个容器被多个项目共用**：这时按 3.3 的引用计数规则，默认不停，需要手动选「停止本项目及依赖」并确认。

### 6.4 Mac 上 O 开头的软件：是 OrbStack，等价于 Docker

本机实测（2026-11-14）：

```
docker context show          → orbstack
docker info (OperatingSystem) → OrbStack
docker --version             → 29.8.2
docker compose version       → v5.5.0
```

**OrbStack 是 macOS 上 Docker Desktop 的替代品，兼容同一套 `docker` / `docker compose` 命令**。所以：

- Windows 上写的 `docker compose up -d` / `docker compose stop` / `docker stop`，在 Mac 上**原样可用**，不需要为 Mac 写第二套逻辑；
- 唯一要改的是项目路径（`/path/to/project`）和 compose 文件位置，这些本来就在档案的 `cwd` 里由 Agent 写；
- `127.0.0.1:5432` 这类端口映射照常，探测层的 TCP 握手无需任何适配。

当前正在跑的容器（也说明为什么归属必须显式登记、不能猜）：

| 容器 | 镜像 | 端口 | compose 归属 |
|---|---|---|---|
| `yanyun-pg` | pgvector/pgvector:pg14 | 127.0.0.1:5432 | 无 label（`docker run` 起的） |
| `yanyun-redis` | redis:8.2.2 | 127.0.0.1:6379 | 无 label（`docker run` 起的） |
| `compose-postgres-1` | postgres:18 | 127.0.0.1:5433→5432 | `project=compose`, `service=postgres`，`healthy` |

容器来源不统一（有的有 compose label、有的只有容器名），而且 5432 / 5433 两个 Postgres 并存 —— 这正是「`stopCommand` 必须由 Agent 写进档案、程序按名字/service 停、共享依赖要引用计数」的现实依据。

## 7. 本轮实现落地（2026-11-14）

需求口径修正：**Agent 不只是「写一次档案」，也能启停**；同时「谁启动的都要能看见、能关掉、关不干净要能发现」。

### 7.1 新增 MCP 工具（`src/core/mcp.ts` / `mcp-meta.ts`）

| 工具 | 作用 | 默认行为 |
|---|---|---|
| `project_start` | 启动已登记项目（依赖先起、等就绪） | 异步发出、立即返回，`wait:true` 才等结果 |
| `project_stop` | 关闭项目 | 按档案 `stopPolicy`，回执带「将停清单 + 残留复检」 |
| `project_discover` | 体检：扫 compose / .env / package.json / ecosystem，列出未登记节点 | 只读 |

三个都进 `FULL_ONLY_TOOLS`（`project_discover` 为只读，进 `READONLY_TOOLS`），启停写 `log_agent_action` 审计。

### 7.2 关闭预演 + 残留复检（`project-runner.ts` / `project-probe.ts`）

- `planStop()`：只算不动手，返回 `targets`（会停）与 `survivors`（保留及原因：shared / keep / 仍被其他运行中项目引用）。页面弹窗与 MCP 回执共用同一份计算，避免「说的和做的不一致」。
- `stopProject()` 停完等 4s（跨过 SIGKILL 宽限期）再探测，仍有端口/容器存活 → 状态带 `residual`，页面标红「没停干净」、托盘显示「⚠ 未停干净」。这是「漏登记」唯一能自动暴露的出口。
- 状态签名加入 `residual`，SSE 会推送变化。

### 7.3 体检（`src/core/project-discovery.ts`）

读 `docker-compose*.yml`（services + 宿主机端口）、`.env*`（`*_PORT`）、`package.json`（start/dev）、`ecosystem.config.js`，产出建议节点：
- compose service → `kind=compose` + `stopCommand: docker compose stop <svc>` + `probe.docker`
- `.env` 端口命中本机容器（按容器名/service 名猜）→ `kind=docker` + `docker stop <name>`
- 主项目节点自动 `dependsOn` 上面这些，批量登记后直接形成「关主项目 → 连带停容器」的图

页面「体检」按钮勾选后走 `POST /api/myprojects/batch`，服务端按「被依赖者先写」多轮重试，避免「依赖项目不存在」。

### 7.4 写入补漏提醒（`project-store.ts`）

不阻断写入，但必须说出来：
- 目录下有 compose 文件却 `dependsOn` 为空
- 启动命令里出现 `docker` 却没有任何依赖节点

### 7.5 顺手修掉的三个真 bug

| 问题 | 影响 | 修法 |
|---|---|---|
| `lsof -ti tcp:PORT` 未限定 LISTEN | 返回的是连上来的浏览器/探活客户端 PID → 归属校验失败 → 外部启动的项目永远关不掉 | 加 `-sTCP:LISTEN` |
| 归属判断只比命令行 | `pnpm dev` 起的 vite 命令行不含路径 → 判为「不像本项目」 | 命令行不匹配时再比进程工作目录（`lsof -d cwd`），并 `realpath` 消除 `/var` 与 `/private/var` 差异 |
| `normalizeCommands` 只认对象数组 | Agent 传 `["npm i","pnpm dev"]` 会被整条丢弃报「缺少启动命令」 | 接受字符串数组 |

### 7.6 测试

`npm run smoke:projects`：体检解析 → 登记 → 启动 → 状态 managed → 关闭无残留 → 外部启动进程识别为 external 并被关闭，19 项断言。既有 `core:test` 221 项全绿。

## 8. 从属模型：一条主档案 + 自动派生子节点（2026-11-14 第二轮）

上一版把「拆几个节点」交给 Agent 判断，结果同一个项目两次能写出不同形状，页面上就是三张平起平坐的卡，看不出谁是谁的依赖。

### 8.1 数据层：`parent`

- 新增 `ProjectRecord.parent`：子节点指向主项目，语义等价于 `dependsOn` 但不需要 Agent 手写。
- `topoOrder` / `resolveDependents` 都把 parent 当成隐式依赖，启动先起子节点、停止先停主节点。
- 子节点没写 `cwd` 时自动继承父项目（容器节点本来就没有自己的目录）。
- `deleteProject`：删主项目时，独占子节点一起删；被别的项目 `dependsOn` 的子节点保留，只解除 parent（防止删掉别人在用的库）。

### 8.2 自动派生（`project-registrar.ts`）

`project_upsert` 默认 `autoDiscover=true`：写入主项目后自动扫目录，按保守规则派生：

| 证据 | 处理 |
|---|---|
| `.env` 端口命中本机容器 | 直接收（kind=docker，`docker start/stop <name>`） |
| compose service + 有宿主机端口 + 镜像像数据库/中间件 | 收（kind=compose） |
| 其余 | 进 `skipped`，说明原因，交给人决定 |

回执带 `derived`（新增了哪些）、`children`（当前挂在它下面的）、`skipped`（没自动收及原因）。编辑（PUT）默认不派生，避免偷偷加节点。

### 8.3 呈现

- 页面：一张卡 = 主项目 + 子节点行。每个子节点显示自己的状态点、端口、容器状态、是否残留，并可单独启停。
- 托盘：`● BuildingAI（含 2 个依赖）`，子菜单里列出各依赖的运行状态。
- 新增 `GET /api/myprojects/tree` 返回折叠结构，页面与托盘共用。

### 8.4 冒烟测试的硬性约束

派生节点里可能包含**真实容器**（`.env` 的 `DB_PORT=5432` 会命中开发机上的 `yanyun-pg`）。因此：

- 冒烟脚本对「自动派生」只做 `planStop()` **预演**，绝不调用会真执行的 `project_stop`；
- 测试目录的 `.env` 一律用不存在的端口号。

> 这条是踩出来的：第一版冒烟用 `project_stop('smoke-auto')` 真跑，把开发机的 `yanyun-pg` 停了。
