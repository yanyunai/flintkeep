# 07 白名单模块设计（整合 easy_whitelist）

> **目标**：把「自动探测本机公网 IP → 更新云安全组白名单」做成 flintkeep 的一个页面，支持**手动点击执行**与**定时自动执行**，且凭据全程不出燧垒。

---

## 1. 背景与目标

- 已有工具：`D:/path/to/scripts/easy_whitelist`（Python CLI，命令 `ew`，PyPI 包名 `EasyWhitelist`）——已能探测公网 IP 并更新腾讯云地址模板 / 阿里云前缀列表。
- 它的短板：命令行操作、凭据走**环境变量明文**、无审计、无法定时、结果无法可视化。
- flintkeep 已有：加密存云 AK/SK（`cloud_account`）、审计（含调用方）、轮换提醒、**阿里云/腾讯云请求签名（已实现）**、Electron 桌面壳。
- 结合后：**凭据不出燧垒 + 有界面 + 可定时 + 全程审计**。

---

## 2. 契合点

| flintkeep 已有能力 | easy_whitelist 的需求 |
|---|---|
| 加密存云账号 AK/SK | 正是它要消费的凭据 |
| 审计 + 调用方记录 | 白名单变更需要留痕 |
| 密钥轮换提醒 | AK/SK 到期提醒天然复用 |
| 阿里云/腾讯云请求签名（`proxy.ts`） | 签名算法可复用 |
| Electron 桌面壳 | 天然承载"点一下就执行"的页面 |

另：目前散落在测试脚本里的**明文 AK/SK**，正是本次整合要消灭的对象。

## 3. easy_whitelist 现状（代码事实）

### 3.1 入口与命令

```
ew [-t | -a] [-p PORT] [-v] <init | list | set> [target_id]
```

- `-t` 腾讯云（默认）／`-a` 阿里云／`-p` 本地 HTTP 代理端口
- `init` 初始化绑定 · `list` 列出并交互选择 · `set` 探测 IP 并更新
- 入口：`EasyWhitelist/__main__.py` → `_core.main()`

### 3.2 凭据来源（关键约束）

| 厂商 | 代码位置 | 取凭据方式 |
|---|---|---|
| 阿里云 | `aliyun/client.py` → `ClientFactory.create_client()` | 读环境变量 `ALIBABA_CLOUD_ACCESS_KEY_ID` / `ALIBABA_CLOUD_ACCESS_KEY_SECRET`，缺失直接 `RuntimeError` |
| 腾讯云 | `tcloud/client.py` → `get_common_client()` | `credential.DefaultCredentialProvider()`（读 `TENCENTCLOUD_SECRET_ID` / `TENCENTCLOUD_SECRET_KEY`） |

> **结论：两边 SDK 都只吃环境变量，没有"传入显式密钥"的接口。** 这是方案 B 必须改造它的原因。

### 3.3 其它实现要点

- **IP 探测**：`detector/detectors.py` —— 并发 GET 多个外网源 + 正则提取 + `dict.fromkeys` 去重。Node 可等价实现（约 40 行）。
- **缓存**：region / 安全组信息存本地 SQLite（`util/db.py`）。
- **腾讯云调用方式**：`CommonClient.call_json(action, params)` 通用 JSON 调用，改造成本低。

## 4. 三条集成路径对比

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 子进程调 CLI** | Node `spawn('ew set')`，AK/SK 塞进 env | 零改动 easy_whitelist，最快 | 依赖 Python + venv 绝对路径；密钥进进程环境（同机可窥）；输出是彩色终端文本，页面无法直接展示；Electron 打包要带 Python |
| **B. Python 桥接** | 新增 `bridge.py`，收 JSON → 调库 → 返回 JSON | 结构化输出，改动较小 | 仍依赖 Python；阿里云 `ClientFactory` 只吃 env，须改造才能传显式密钥 |
| **C. Node 原生重写** ✅ | flintkeep 直接调云 API | **无 Python 依赖**；密钥全程在内存、不经 env/命令行；结构化、可测试、可审计；打包干净 | 需自行实现签名与 API 调用 |

### 推荐：方案 C

理由：

1. 目标是做成 flintkeep 的**一等公民页面**，而非外挂进程。
2. 核心技术已具备——阿里云 RPC HMAC-SHA1 签名在 `proxy.ts` 中**已实现并验证**；仅腾讯云 TC3-HMAC-SHA256 需新写（约 60–80 行），且有官方向量可验证（参照当初验 AWS SigV4 的做法）。
3. 安全性显著更好：凭据不落 env、不落盘、不进命令行。

---

## 5. 方案 C 技术要点

### 5.1 需要调用的 API

| 厂商 | 模块（版本） | 操作 |
|---|---|---|
| 腾讯云 | `vpc`（2017-03-12） | `DescribeAddressTemplates` / `ModifyAddressTemplateAttribute` |
| 阿里云 | `ecs`（2014-05-26） | `DescribePrefixLists` / `ModifyPrefixList` |

### 5.2 签名

- **阿里云**：ECS RPC 风格 HMAC-SHA1 —— 复用 `proxy.ts` 的 `applyAliyunSignature`（已验证）。
- **腾讯云**：TC3-HMAC-SHA256 —— 需新写，**必须先对齐官方向量**再接真实账号。

### 5.3 凭据传递（最关键的安全设计）

```
燧垒(加密) ──内存──> 签名函数 ──> 云 API
        ↑
  不写 env / 不落盘 / 不进命令行
```

从 vault 取 `cloud_account` 的 AK/SK，内存中使用后即弃。每次执行写审计：`哪个云账号 / 哪个模板 / 旧IP → 新IP / 成功失败 / 时间`。

### 5.4 只在 IP 变化时才调 API

先探测比对，**IP 没变就不发起修改请求**——否则定时执行会打满云 API 的 QPS 限额并被限流。

## 6. 页面设计（新增「白名单」tab）

现有 tab：资产 / 审计 / MCP / 设置 → 增加 **白名单**。

| 区块 | 内容 |
|---|---|
| 顶部 | 当前探测到的公网 IP + 「重新探测」按钮 |
| 任务列表 | 云账号 + 厂商 + region + 安全组 ID + 模板/前缀列表 ID + 上次执行结果 + 启用开关 |

**绑定数据（仅含 ID，无密钥）** → 存 `dataDir` 下的普通 JSON 即可，无需加密。

## 7. 定时任务方案

| 方案 | 生效条件 | 评价 |
|---|---|---|
| **应用内定时器**（Node 侧调度） | Electron 运行时 | **首选**：密钥不出内存，实现简单 |
| **系统级**（Windows 任务计划 → headless CLI） | 关机/关界面也执行 | 次选：需把 `VAULT_PASSPHRASE` 放进 env；提供 CLI 命令由用户自行挂载 |

**建议**：先做应用内定时器（覆盖绝大多数场景），同时暴露一个 CLI 命令，需要时由用户挂到系统任务计划程序。

---

## 8. 风险与注意事项

1. **只在 IP 变化时才调 API** —— 避免云 API QPS 限流。
2. **腾讯云 TC3 签名必须对齐官方向量**后再接真实账号。
3. **权限**：阿里云 RAM 需 `ecs:ModifyPrefixList`；腾讯云需地址模板写权限。权限不足会静默失败。
4. **`init` 与 `set` 要区分**：`init`（把模板绑定到安全组规则）只需执行一次；`set` 才是日常更新模板内容。页面不要把两者混为一谈。

### 定时调度的两种模式（已都实现）

| 模式 | 生效条件 | 使用方式 |
|---|---|---|
| 应用内调度 | flintkeep 运行时 | 白名单页勾选「启用」并选间隔；服务端 60s 轮询，到点执行 |
| 系统级调度 | 关机 / 关界面也执行 | 系统任务计划挂载 `npm run whitelist:run`（需设 `VAULT_PASSPHRASE`） |

两者共用同一套 `runAll` 逻辑：IP 未变化则跳过调用，不会因高频定时打满云 API。

### 与 easy_whitelist 的关键差异（改进点）

1. **替换语义**：easy_whitelist 的阿里云只做 `AddEntry` 追加，旧 IP 会长期滞留在白名单；本模块先 `DescribePrefixListAttributes` 取现有条目，再「移除旧 + 加入新」，保证白名单里只有当前 IP。
2. **IP 未变化不调 API**：`runBinding` 先与 `lastIp` 比对，相同则跳过调用，避免打满云 API QPS。
3. **凭据不出燧垒**：AK/SK 从 vault 内存取用，不写 env、不落盘、不进命令行。

### 2026-10-22 追加：地域 / 目标 ID 改自动下拉（腾讯云可配）

**问题**：用户要给腾讯云「示例账号」配白名单，但表单要求手填**地域**（`ap-guangzhou`）和**地址模板 ID**（`atm-xxxx`），都是云上生成的字符串，不知道从哪复制、极易填错。

**改动**：

- 新增 `GET /api/whitelist/options?assetId=&provider=&region=`，用该账号 AK/SK（内存取用）实时拉真实列表：
  - 腾讯云：`DescribeRegions` → 地域；`DescribeAddressTemplates` → 地址模板（带模板名 + 现有 IP 条数）
  - 阿里云：`DescribeRegions` → 地域；`DescribePrefixLists` → 前缀列表
  - 不带 region 只拉地域，带上再拉该地域下的目标（两步联动）
- `whitelist.ts` 新增 `listWhitelistOptions()` / `tencentListRegions()` / `tencentListAddressTemplates()` / `aliyunListRegions()` / `aliyunListPrefixLists()`
- 前端：厂商/账号变化 → 自动拉地域；选了地域 → 自动拉目标；已保存值若不在新列表中会保留成「（已保存）」，不会被清空
- **拉取失败不静默**：显示错误 + 提示（腾讯云多为缺 `QcloudVPCReadOnlyAccess`，阿里云多为缺 `AliyunECSReadOnlyAccess`），并退回手填

**踩坑（已修）**：`DescribeRegions` 是全局接口、本身不需要地域，但**腾讯云网关要求 `X-TC-Region` 头非空**，之前传空串直接被拒 → `MissingParameter: The request is missing the required parameter 'Region'`。现加 `TC_DEFAULT_REGION = 'ap-guangzhou'` 兜底（优先所选地域 → 账号资产上的 `region` → 默认值），`runBinding` 也加了「缺少地域」的明确报错。
